# SePay + Cloudflare implementation reference

Use this reference only when SePay is the payment provider and Cloudflare Worker/D1 is the backend.

## SePay prerequisites

Before configuring a webhook:

1. Link the intended receiving bank account in SePay.
2. Configure a payment-code structure/prefix that matches the codes generated by the Worker. SePay's payment-prefix field accepts letters only, so validate the prefix as alphabetic (prefer uppercase ASCII, for example `TTN`) and put any digits only in the generated suffix. Preserve the prefix in the QR transfer memo; if SePay limits the extracted variable part to a fixed number of digits, apply the limit to the suffix rather than stripping the prefix.
3. Deploy the Worker to a public HTTPS URL.
4. Create a Money in webhook for the intended bank account.
5. Keep `application/json`, enable retry, and use HMAC-SHA256 in production.
6. Store the generated HMAC secret immediately in Cloudflare Secret storage; SePay masks secrets after saving.
7. Use SePay's test-send action before any real transfer.

## QR construction

Generate one QR per order from server-returned values. SePay's QR guide uses:

```text
https://vietqr.app/img?acc={ACCOUNT_NUMBER}&bank={BANK_CODE_OR_NAME}&amount={INTEGER_VND}&des={URL_ENCODED_PAYMENT_CODE}
```

Do not construct the final payable amount from editable browser values. The Worker calculates it and returns the QR inputs.

## Webhook payload fields used for matching

Relevant transaction fields include:

```json
{
  "id": 92704,
  "gateway": "Vietcombank",
  "transactionDate": "2024-07-02 11:08:33",
  "accountNumber": "1017588888",
  "subAccount": "",
  "code": "ORDER_CODE",
  "content": "ORDER_CODE chuyen tien",
  "transferType": "in",
  "description": "...",
  "transferAmount": 149000,
  "accumulated": 0,
  "referenceCode": "..."
}
```

Rules:

- Use `id` as the webhook deduplication key; retries and manual replays keep the same transaction ID.
- Match orders using `code`, which SePay extracts according to the configured payment-code structure. Keep the QR memo and stored order code aligned with the configured prefix (for example, display `DEMO-1234567` while transferring `DEMO1234567` only if that is the exact configured structure).
- Require `transferType === "in"`.
- Separate the QR destination (`BANK_ACCOUNT_NUMBER`) from the settlement account (`BANK_SETTLEMENT_ACCOUNT_NUMBER`) when a bank supports an alias, VA, or TKP. Preserve both as exact strings: aliases may be alphanumeric and account numbers may have leading zeroes.
- Match bank-specific structured tuples before any prose fallback. For a BIDV alias/VA payload, require the configured gateway, `accountNumber === BANK_SETTLEMENT_ACCOUNT_NUMBER`, and `subAccount === BANK_ACCOUNT_NUMBER`; also permit the direct-account shape only when `accountNumber === BANK_ACCOUNT_NUMBER`. This prevents a valid transfer to a different VA on the same settlement account from being credited.
- Use an authenticated `content`/`description` fallback only when provider documentation says the relevant structured identifier can be absent. Never use prose merely to override structured fields that disagree. Log masked lengths/last characters and the matching path; never log full financial identifiers.
- Treat `transferAmount` as an integer VND amount.
- Preserve the raw payload for audit.

## HMAC verification

SePay's HMAC scheme signs:

```text
{X-SePay-Timestamp}.{raw_request_body}
```

Verify the hexadecimal HMAC-SHA256 value from `X-SePay-Signature`, whose form is:

```text
sha256={hex_digest}
```

Reject timestamps outside a five-minute window. Compare signatures in constant time where the runtime permits. Read `request.text()` once and verify that exact string before `JSON.parse`; do not parse then stringify.

## Response contract

For a successfully received and accepted webhook, SePay requires all of:

- HTTP `200` or `201`;
- JSON body exactly equivalent to `{"success":true}`;
- response within the provider timeout.

An empty body, redirect, `202`, or a different JSON shape is treated as failure and can trigger retries. With SePay auto-retry enabled, non-2xx deliveries are retried on a Fibonacci schedule (about 1, 2, 4, 7, 12, 20, and 33 minutes cumulative). Deploy a validated receiver fix before the next window and monitor D1; manual replay is useful but must not be the sole recovery path. Return quickly and use `ctx.waitUntil(...)` for CRM synchronization or other non-ledger work.

Authentication failure, malformed payload, or invalid required data should receive an appropriate non-success response. An already-recorded duplicate transaction should return the success contract without repeating state changes.

## SePay test-send diagnostics

Diagnose SePay's test-send result by the receiver stage it reached:

- `401` means HMAC headers, timestamp freshness, or Secret Key failed before the payload was trusted.
- `422` after valid HMAC means a business invariant such as `transferType`, gateway, or recipient account rejected the authenticated payload.
- SePay may wrap any non-2xx receiver response as cURL error 22 / HTTP 0 in its UI; use the embedded HTTP status and Worker logs rather than treating `HTTP 0` as a network failure.

SePay's dashboard test-send can use a synthetic authenticated payload with `gateway="SePay"` and `accountNumber="0000000000"` instead of the selected live bank account. A receiver that correctly enforces the real recipient will otherwise return `422`. Handle this with a narrow test-only branch **after successful HMAC verification**: accept only the exact synthetic marker pair, return `{"success":true}`, and do not create an order, webhook-ledger event, or payment mutation. Keep the normal `BIDV`/account matching path unchanged for every real payload.

When diagnosing a mismatch, log only `transferType`, gateway, masked first/last characters, and identifier length. Never log the HMAC secret, full account number, or raw payload. Stop the temporary tail after one capture. Re-query D1 after the probe and require zero test mutations before enabling checkout.

## D1 schema invariants

Keep two canonical tables:

- `orders`: opaque ID/public token, unique payment code, customer/shipping snapshot, unit price, shipping fee, total, status, paid amount, timestamps, and CRM sync status.
- `webhook_events`: provider transaction ID as primary/unique key, matched order ID when available, raw payload, processing result, and timestamp.

Add indexes for payment code, public token, and status/created time. Indexed lookups prevent D1 row-read limits from being consumed by full-table scans.

Use an atomic insert-or-ignore for the webhook event before mutating the order. If the event already exists, acknowledge success and stop.

## Cloudflare commands

Verify identity:

```bash
npx --yes wrangler@4.133.0 whoami
```

Create and initialize D1 only after the database name is approved:

```bash
npx --yes wrangler@4.133.0 d1 create <database-name>
npx --yes wrangler@4.133.0 d1 execute <database-name> --remote --file=schema.sql
```

Store secrets interactively; never put secret values in shell history:

```bash
npx --yes wrangler@4.133.0 secret put PAYMENT_WEBHOOK_SECRET
npx --yes wrangler@4.133.0 secret put CRM_API_TOKEN
```

Deploy and verify external state:

```bash
npx --yes wrangler@4.133.0 deploy
curl --retry 3 --retry-all-errors -sS https://<worker-domain>/health
```

After deployment, configure SePay with:

```text
https://<worker-domain>/api/payment/webhook
```

Run test-send, then verify both the SePay delivery log and the Worker/D1 result before claiming the webhook is connected. For a failed live delivery, read the response body first: it often identifies the exact rejected invariant. Fix that invariant, wait for an enabled automatic retry, and verify the order plus deduplicated event in D1. If retries are exhausted and replay is unavailable, reconcile through SePay's authenticated transaction API or a protected admin path only after independently verifying transaction ID/reference, amount, receiving account, timestamp, and payment code; do not mark paid from a screenshot or customer claim alone.
